# Neovim r28b：DAP 与 which-key

基于已合并、已应用的 `fd8ecac`，工作分支 `nvim-r28b`。本轮只修改编辑器源码、检查和文档；没有提交、切换系统配置、修改 SDK 或连接板卡调试服务。B+C 的细顶栏、胶囊标签、按需侧栏、居中搜索和单行状态栏保持原有结构。

## 主代理初审后的测试修正

原先对 `nvim_get_keymap()` 返回表做重复 lhs 检查，只能观察覆盖后的结果，不能证明注册过程中没有冲突，已删除该无效断言。

现在针对本轮关键映射验证最终行为：全部 lazy domain 加载及离线 LSP attach 后，在当前 buffer 和合成 LSP buffer 两个上下文中检查 27 个 Debug/F-key 映射。锁定 lz.n 即使插件已加载仍保留首按包装，因此测试先通过真实 `feedkeys` 分发按键（仅 stub DAP 动作边界，不启动会话），再断言最终 callback 与 utility spec 声明的函数对象一致。`<leader>?` 调用最终有效 callback，以 spies 验证依次加载 `which-key.nvim`、执行 `show({ global = true })`。反例实际覆盖全局 `<leader>db`、添加 buffer-local `<leader>db`/`<leader>?` 遮蔽，确认断言失败后恢复映射。

证明范围：本 fixture 加载状态和这两个 buffer 下的关键映射最终归属、leader 分组前缀未被占用，以及 which-key 实际虚拟树没有重复项。它不证明所有注册历史无覆盖，也不覆盖任意后续 FileType/用户插件/其他 buffer 的映射。没有为此重构产品配置。

补充断言直接运行通过（`ownership/direct.log`），并已在 Nix `neovim` check 中执行通过（`ownership/neovim-check.log`）。独立 reviewer 对本次修改只读复核，未发现确定缺陷，未执行 Nix/GUI。

本次续跑只修改测试和报告，运行时配置未变。性能与 83 张截图继续引用下文已执行的最终产品测量，不将它们冒充本次新增采样；新增测试带来的配置包 store 路径变化另以最终构建输出记录。

## 固定工具与包边界

`debug-tools.nix` 从现有 `pkgs` 实例取包，不新增 nixpkgs 实例、不改锁文件、不在运行时下载：GDB 17.2、codelldb 1.12.1、debugpy 1.8.20、jdtls 1.58.0、vscode-java-debug 0.59.0、vscode-java-test 0.45.0。nvim-dap-view 1.1.1；OSV、nvim-dap-virtual-text、nvim-jdtls 使用锁定 nixpkgs 插件源码。

`patches/gdb-dap-detach.patch` 是本轮唯一新增外部源码补丁：`disconnect(false)` 在 GDB 线程显式 detach 后再 shutdown；true 保留 kill；无 inferior 时不 detach。原 GDB binary/ABI 不重编译。Nix 构建应用精确源码 hunk；`tests/debug_gdb.lua` 通过产品 wrapper 载入真实 patched Python module 和 request decorators，只 mock GDB 命令执行边界，检查线程归属与三个分支。它不是完整远程硬件测试。

最终 normal 包的真实 loopback 证据为 `.work/r28b-nvim/remote-validation/final-stopped/result.json` 和 `final-running/result.json`，两场均 `explicitRemoteDetach=false`、42→43、目标输出 `answer=43`、session closed、无错误/deprecated；JSON 记录实际 generated GDB wrapper 及 patched data-dir。

中间轮次真实 loopback 证据位于 `.work/r28b-nvim/remote-validation/normal-build/`（停止态）和 `running-run/`（运行态），均 `explicitRemoteDetach=false`、目标输出 `answer=43`、错误/deprecated 为空。这两次使用 Round 2 的 reduced-motion 包 `zpxrbc5i1r0fgbrhdbbp6kghvzzi0v6f-neovim-0.12.6`，与 normal 共用适配器实现；`normal-build` 是实验目录名，不代表该包是 normal。父目录旧 `result.json` 属于手动 detach 实验，不作为补丁通过证据；`raw-disconnect.json` 保留修复前失败。

## 限制、待实机验收与执行偏差

- `192.168.7.1` ping 可达，但没有获知可供本轮使用的 gdbserver 端口/ELF。已询问是否有专用目标，未收到授权目标信息；没有扫描端口、attach、停止或重启另一个代理的板上进程。STM32 实板、MP157 ABI/sysroot/共享库映射、实际外设寄存器仍待硬件验收。loopback 只证明 GDB remote 协议和 disconnect 行为。SVD 可选，本轮未添加。
- C/C++/Rust 的本地 PID attach、Python 外部 debugpy attach 配置已提供，但没有逐一对用户进程实测；已验证每种语言至少一个完整最小 launch/attach 会话。Lua 的 launch 本身是对自建 Neovim OSV server 的 attach。Java 主类、测试类、最近测试均实际执行。项目自身构建系统、依赖和源映射仍由项目负责。
- 本轮不安装 OpenOCD、gdbserver 服务或 SDK，不烧录、不复位板子；适配器已由 Nix 提供。远程主机服务需要使用者提前准备。
- 锁定 nvim-dap 对 executable adapter 关闭先发 SIGINT，5 秒后才兜底 SIGKILL。早期 headless harness 在 sessionClosed 后立即 qa!，来不及执行该 timer，留下 3 个只属于本轮 HOME 的 GDB orphan；已核对无子进程并清理。修改 harness 保留编辑器 5600 ms 后重测 running disconnect，`remote-validation/final-running-clean/result.json` 记录目标正常输出、无错误且 `remainingGdbProcesses=[]`。这是上游关闭时序的限制：断开后立即退出编辑器仍可能留下适配器，保留编辑器约 6 秒可完成清理；本轮没有对全局进程或用户 GDB 做扫描式清理。
- 需在用户实际终端验收 F-key/Shift-F-key 转发与 tmux、不同键盘布局；私有 Kitty 中已验证布局/会话，未接管用户桌面。
