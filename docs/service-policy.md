## 实际运行抽查与声明差异

本次只读检查 `systemctl list-units/list-sockets/list-timers`、user manager、相关 unit 属性、进程列表、当前用户 Linger 状态、用户 unit 文件和仓库声明，没有读剪贴板、密钥、模型权重或应用凭据。当前 Mango/graphical session active，`mayon` 的 user manager `Linger=no`。系统侧抽查到 NetworkManager、resolved、Bluetooth、Clash Verge、earlyoom、greetd、libvirtd、NVIDIA persistence、power profiles、thermald、upower 等 active；SSH socket listening；Docker prune timer waiting；libvirt Unix sockets 可触发 libvirtd。用户侧抽查到 Docker、PipeWire/WirePlumber、fcitx5、clipboard bridge、Noctalia 子进程和 portal/keyring 相关进程。portal 的 active 状态是本次会话快照，不证明每个登录后都常驻。

当前运行状态**不完全等于当前工作树声明**：user manager 还在运行 `~/.config/systemd/user/llama-cpp.service` 和两项 `cliphist-watch-*.service`，其中前者监听 `127.0.0.1:8080`，后两项采集文本和图片剪贴板；这三份文件来自持久化用户配置目录，不在当前仓库的 Nix 模块声明中。`modules/home/services/cliphist.nix` 与本地 llama-cpp 模块已从工作树删除；Noctalia 当前声明采用内建历史，refactor plan 也记载删除本地模型服务配置，但保留模型权重和数据。故这三项是待后续 Den 迁移确认的旧世代/手工运行态，不能把它们误写成新目标必需服务，也不能因此清理用户文件或数据。当前工作树也仍有用户配置改动；此快照不能证明下次系统重建后的最终运行态。

同样，当前运行的 `cliphist` unit 与声明不一致，不能把 Noctalia 内建历史解释成它已替换正在运行的旧 watcher。后续应用配置后，应专门核实其退出，并由用户决定旧历史数据保留方式。本次没有 stop/restart 这些进程。

AI 软件清单里的 Codex、Grok Build、OpenCode、Grok Bot、DeepSeek Harness 和 Neovim CodeCompanion 是 CLI、桌面程序或插件声明，不是本仓库声明的 daemon；Quill 插件可调用 OpenCode CLI。见 [AI agents](../modules/home/programs/dev/ai-agents.nix)、[Grok Bot](../modules/home/programs/dev/grok-bot.nix)、[Noctalia/Quill](../modules/home/wm/mango/noctalia.nix)。当前 `llama-server` 是上述用户配置目录里的独立常驻进程。运行时也有 Codex app-server 子进程，但它不是本仓库 systemd 服务声明，生命周期由 Codex 应用管理。根据既有决定，本地模型服务保持删除；后续只核对并处理遗留 unit/进程，不重新讨论是否部署。

## Den 多主机目标策略

服务策略应由明确的 host/account binding 选择，完整功能 aspect 自己携带启动配置、依赖、资源边界、日志和秘密接口。主机事实（平台、设备、磁盘）不能推导出服务需求；安装工具也不能自动代表启用 daemon。比如远程 Docker CLI 与本地 Docker 引擎、virt-manager 客户端与 libvirt 宿主服务应可独立选择。一个账号选桌面功能时才得到 Mango、Noctalia、portal、keyring、IME、音频、剪贴板等用户体验；服务器账号不因同一身份而继承 GUI 用户 session。

建议每个服务功能在 Den 实现中记录这些字段或等价证据：owner（system/host、account/user、session/application）、唯一启动方和依赖、常驻还是需求触发、停止边界、重启条件/间隔/上限、CPU/内存/显存/IO 或任务并发限制、日志位置与轮转、秘密的运行时来源与读取身份、持久数据位置及迁移负责人。不要为“低资源”写臆测数字；没有测量值时先标注待基线，不能把构建成功当作运行成本结论。

具体目标如下：

- **无头服务器默认不启用桌面专属用户 unit 或 GUI 自动启动依赖。** 不选择 Mango、Noctalia、greeter、fcitx5、clipboard bridge/history、桌面 portal/Secret Service agent、桌面通知、GVFS/缩略图和 Noctalia 插件。NixOS 可安装标准 `graphical-session.target`、`user@.service`、`systemd-user-sessions` 等系统设施；验收应检查 target/wants、D-Bus activation 和桌面专属用户 unit 的依赖图，确认它们不被自动拉起，而不是要求这些标准 unit 不存在。若某远端桌面/GUI 是明确目标，再以独立功能整体选入；不能靠启动用户 linger 常驻 GUI。
- **当前笔记本保留 Mango + Noctalia 的完整体验，并监督 shell 生命周期。** 启用锁定 Noctalia HM 模块提供的 `noctalia.service`；仅对该 unit 的 `Unit.PartOf`、`Unit.After`、`Install.WantedBy` 做字段级 list 替换（`lib.mkForce [ "mango-session.target" ]`），不强制覆盖整个 service/HM，不改全局 `wayland.systemd.target` 或其他 unit。移除 `noctalia &`，由 unit 统一管理进程；Mango 自身和 HM autostart 都可能请求启动 target，不把它们误写为两份 Noctalia 启动命令。HM autostart 暂保留非空 `:` 以保留上游补充同步钩子，但它不再被视作启动 target 的必要条件或环境先决保障。给 Noctalia 配置 `Restart=on-failure`、2 秒重试间隔和每 60 秒最多 3 次启动限制；超过预算后保留 failed 状态供用户查看/恢复。启用 `launch_apps_as_systemd_services = true`，实际故障注入验证已启动应用存活。session target 结束应停止 Noctalia 和 session-only 服务。保留内建 clipboard history 为唯一历史功能及独立跨 X11/Wayland bridge；bridge 保持 `Restart=always`、2 秒重试，并显式设置每 60 秒最多 3 次启动限制。应用前后核对遗留 cliphist watcher 与数据。
- **环境必须在消费者启动前可用。** 保留当前 `systemd.user.sessionVariables` 的安全共享键，由 HM 生成 `environment.d/10-home-manager.conf`，供新 user manager 在 Mango 之前加载；同一类型化数据也供 home、Noctalia unit 显式 `Service.Environment` 和启动器所需环境消费。键包括实际所选功能需要的 `NIXOS_OZONE_WL`、`QT_QPA_PLATFORMTHEME`、GLFW/SDL/XMODIFIERS 等输入法变量及所选 JDK 的 home 键，不把固定一批 Java 版本强加给其他绑定。不得导入完整 home 环境、`--all` 或秘密。动态 DISPLAY/WAYLAND/XDG/XCURSOR/Mango signature 仍使用 compositor 的实际值；检查 C 启动路径与 HM 的变量集合差异。**不能只在 autostart 扩展白名单后就认定无竞态**：Mango C 路径可能先启动 Noctalia。应用到已有 user manager 时，要在重启会话/服务前显式同步相同安全白名单到 systemd 与 D-Bus，或通过完整注销重登录确保新环境生效；`daemon-reload` 不代表环境已刷新。验收对比 unit 环境、user manager 和 launcher 启动的 Qt/Electron/输入法客户端，冷登录和旧会话更新都需测试。
- **portal 按真实接口选 backend。** Mango 的 screencast/screenshot 走 wlr；文件选择使用当前可工作的 GTK backend；Secret portal 依赖 GNOME Keyring。Portal 本身应由 D-Bus/portal 使用需求激活，不为看起来完整而将所有后端强行常驻。无头服务器不带这些图形接口。
- **输入法、网络、音频、蓝牙按 host 能力选择。** fcitx5/Rime 是登录用户 session 工作负载；NetworkManager/resolved 是主机连网基础；PipeWire/WirePlumber 服务于本地媒体/语音；Bluetooth 只在有无线设备/用途时启用。服务器默认只接入其实际网卡、DNS、音频、蓝牙、安全和带外管理设计。
- **Docker 与虚拟化按宿主/客户端分别选择。** Laptop 保持当前 rootless daemon 与周期 prune，并记录 timer 上次/下次运行、实际删除对象和容器/volume 数据责任；保持当前 `mayon` user manager 生命周期，不新增 linger，也不新增注销时的自定义停止/清理动作。最后一个 session 结束后 `Linger=no` 会令 user manager 退出，Docker daemon 随之停止；不承诺容器跨最后注销继续运行。Docker 客户端可以独立安装/配置而不启用本地 daemon。libvirt daemon采用 socket 需求触发语义；关闭 `libvirt-guests` 只代表不启用 NixOS guest 生命周期 helper。目标不新增 domain autostart，保留现有 domain autostart 数据不变；对已有 domain 只读核对，对新 domain 不替用户设置自动启动。系统休眠保持平台当前语义，不无条件暂停/关闭 VM、容器或游戏，也不强制 inhibit；若用户选择的任务长时间不可恢复，可提示并提供可选 inhibit，由用户决定是否继续休眠。服务器只有承担本地容器/VM host 工作负载才启用对应 daemon。
- **SSH 由服务器用途显式启用。** 只开放指定地址/端口和防火墙策略，key-only、最小账号权限，禁止 root 和交互密码。SSH authorized public keys 可作为公开配置放入 Nix/Git/store，前提是接受其公开性；私钥、API token 和其他凭据不得进入 Nix 字符串/store/log，应由运行时 secret/密钥管理提供。客户端包和服务器 daemon 拆开。当前笔记本的 socket 可留作关闭端口下的需求监听或按最终威胁模型关闭，Den 重构不能把它误转为公网开放。
- **本地模型保持已确定删除的服务配置。** 重构不重新声明或启动本地 llama.cpp/model router；应用配置后只读确认遗留 unit/进程状态，既有模型权重和历史数据继续保留。服务停用与数据删除分开，不重新发起部署意向选择。
- **休眠/关机保持现有系统语义。** 会话注销停止 session-bound 服务；系统休眠不主动刷新剪贴板、暂停/关闭游戏、容器或 VM，也不自动拒绝休眠。对长时间不可恢复任务，可告知用户并提供可选 sleep inhibitor；继续休眠由用户决定，不自动杀死任务。电池低于阈值触发 suspend 的现有 Noctalia hook 仅在电池放电跨越 5% 阈值时调用系统 suspend（见 [Noctalia 电池 hook](../modules/home/wm/mango/noctalia.nix)），未来迁移要保持事件语义并验证唤醒/恢复，不把该 hook 当服务。
- **失败恢复有预算。** 短命辅助进程按任务重试并限频；GUI 应用不得无限重启；基础系统 daemon 采用对应模块/服务管理器定义的恢复机制；数据型服务记录退出码、是否有未完成任务和人工恢复步骤。restart 策略、启动依赖、`PartOf`/`BindsTo` 和启动方式应从锁定实现或生成 unit 验证，不凭名称猜 socket activation。
- **日志不携带秘密或用户内容。** system/user journal 记录 unit 状态、启动失败、耗时和退出码；应用按功能另定日志与轮转。日志不得包含剪贴板正文、访问 token、私钥、模型 prompt/对话正文或 secret 文件内容。加密输入由 sops-nix 按 owner/mode 渲染到运行时；服务只拿必要路径或文件描述符，不把 secret interpolate 到 derivation、命令行和 journal。

## 基线与验收协议

性能与续航没有由当前配置文件或这次状态快照证明，本文不宣称服务占用或耗电数值。重构前在实际系统先采集桌面空闲、VM/Docker/音频/蓝牙/剪贴板负载和无 GUI 目标机基线；重构后在同一工作负载与尽量一致的接电/电池、显示器、网络和 power profile 条件下复测。记录每次测量的 NixOS generation、系统/模块版本、内核、包集合和变更清单；版本不能完全一致时，不把差异归因于服务增删，须解释不同变量及其可能影响。至少记录 `systemctl status` / `systemd-cgtop` 或 `/proc` 的 unit CPU、RSS、峰值、IO、进程数，`journalctl` 的启动次数/重启间隔，电池场景用同样时长与电源 profile；采样窗口、命令、硬件和结果存入当次迁移记录，并说明波动与测量限制。

每个目标 host 通过以下验收后才算服务策略完成：

1. 对照生成的 system 与 user unit，确认所选、未选、D-Bus-activated、socket-activated、timer-activated 项与 Den 选择一致；每一项都能指出 owner 和真实触发方。
2. 桌面从登录到注销测试 Mango/Noctalia、IME、portal 文件选择与截屏、Secret Service、两方向剪贴板文本/图片；确认只有一个 Noctalia unit/进程启动方，Mango C 路径与 HM autostart 的 target 请求幂等；扩展环境在二者可能触发消费者之前已通过 environment.d/显式服务环境提供。不能用 autostart 的先后顺序替代首次启动环境验证。注入一次 Noctalia 失败确认有限重试和 start limit；检查 shell 重启不会意外结束 launcher 启动的应用。注销后确认 session-only unit 停止。无头服务器检查 activation、target wants 和依赖图，确认没有桌面专属 user unit 或 GUI 自动启动依赖；标准 target 与用户 manager unit 可以存在。
3. Docker timer 只在预期账号下运行；测试使用容器与数据不被 prune；libvirt 按 socket 触发且没有新增 domain autostart；对现有每个 domain 的 autostart 属性做只读核对。确认休眠保持既有系统语义，长任务提示/inhibit 只有在用户选择时使用。
4. 在本机及远程网络验证 SSH listener、firewall 和认证实际组合；服务器 SSH 只允许批准的 key/账号，日志可审计且无秘密内容。
5. 对声明了 restart 的 unit 注入一次可恢复失败并观察是否按策略恢复；对不应自动重启的 GUI/任务验证失败会留下可读状态而不会无限循环。timer 检查上次/下次时间和失败日志。
6. 比较记录过各自 generation、内核、包集合与电源条件的同场景资源基线；解释无法控制的版本差异，确认增减的 daemon 与目标工作负载匹配；任何阈值或资源额度来自测量/服务需求，不从其他主机复制。
7. 确认应用状态、剪贴板历史、容器 volume、VM 镜像、模型权重、keyring、授权密钥未被包移除、服务停用或日志轮转意外删除。

本轮没有实施这些目标配置、构建或切换系统；没有停止现存旧世代用户 unit，没有测试服务故障注入、网络连通性、真实休眠/唤醒、音频设备、蓝牙设备、Docker prune 删除范围、VM 客体或服务器行为。当前服务清单是这一时点的只读快照；实际 Den 功能实现后仍须在相应 host 上按上述协议验证。
