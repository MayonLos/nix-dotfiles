# Legion laptop hardware

Configures the Lenovo Legion hardware stack: boot/kernel settings, firmware, Intel video, NVIDIA PRIME offload, Bluetooth, power, memory, and hardware-specific GPU policy. Inputs are host facts from `host.facts`, including system, Intel/NVIDIA bus IDs, GameMode GPU index, and mpv hardware decoder. The feature does not embed a host's measured values.

The paired `legion-laptop-user` aspect reads host GPU facts to configure mpv decoding and install Lenovo Legion controls. It grants only its selected account the `legion-conservation` group and installs the public CLI `legion-conservation status|toggle`. `status` prints `养护` only when enabled; `toggle` writes 0/1 to the single ideapad attribute, rejecting missing, ambiguous or invalid devices. The host aspect declares that group and a platform/ideapad_acpi udev rule which gives it write access to `conservation_mode` on add/bind/change. No runtime sudo, group creation, daemon or boot-time change of the charge policy is used. Permissions and account membership take effect only after applying the configuration and refreshing the login session; they were not changed during implementation.

The laptop memory policy keeps earlyoom (`5%` available RAM and `10%` free swap) as the single userspace OOM policy and disables the otherwise idle NixOS systemd-oomd. zstd zram retains a logical capacity of 50% of RAM (allocated on demand); `vm.swappiness=100` gives cold anonymous pages equal reclaim weight to file cache, and `vm.page-cluster=0` avoids speculative swap reads/decompression. These settings are policy choices, not a measured build-speed improvement; application/build memory can still exceed available capacity.

Nix local build concurrency is capped at two derivations with eight workers each, rather than 28 derivations each using all 28 logical CPUs on the 31 GiB laptop. This reduces oversubscription while leaving room for interactive work; packages may ignore the worker hint, and evaluation memory is not capped. Large single-package builds can take longer. The ext4 root uses `noatime` to avoid access-time metadata writes; file content and modification times are unaffected. `/tmp` keeps the existing 50% tmpfs ceiling and Nix daemon builds continue in `/var/tmp`.

Power profiles, lavd's load-based autopilot, Intel driver defaults, NVIDIA offload and the persistence workaround remain unchanged. No AC/battery switching hook is declared; fine-grained NVIDIA runtime PM is disabled pending external-monitor, CUDA, gaming and suspend validation. Runtime sysfs queries during the 2026-10-29 audit showed the NVIDIA device in D0, so the declaration must not be described as verified D3cold power-off.

The host aspect owns kernel/driver/system declarations; hardware facts are supplied by inventory. `contract.nix` defines the host facts schema. `checks.nix` is the public test hook; `default.nix` is the feature entry and other imported Nix modules are private. The CLI's runtime file is the kernel-owned `/sys/bus/platform/drivers/ideapad_acpi/*/conservation_mode`, not a managed user config. A desktop consumer may call the CLI but does not own the hardware permission policy.

Removing the feature withdraws driver, boot, and hardware policy declarations on the next system generation. It does not delete user files, firmware, laptop state, or NVIDIA/Steam profiles; removing drivers while the machine is running requires a later deliberate system switch and reboot.

Removing the user aspect withdraws its group grant and CLI. Removing the host rule does not reset the current firmware charge setting or retroactively revoke a sysfs mode until device recreation/reboot; no removal hook writes charge state.

### Boot audit (2026-10-30, no runtime change)

The running boot still spends 3.185 s in stage-2 `systemd-modules-load`, followed by firewall (213 ms), NetworkManager (801 ms) and greetd; graphical.target is reached at 6.391 s of userspace. The NVIDIA modules are the last entries (nvidia, modeset, UVM, DRM). `nvidia-persistenced` starts after module loading and is not on that measured critical chain. Boot-time registration succeeded in this boot; the user's later GPU power-off/absence is not evidence it was absent during boot.

The locked NixOS NVIDIA module explicitly loads UVM for CUDA and DRM/modeset for PRIME/display support. Keeping persistence and stage-2 loading preserves the known shutdown workaround, externally wired NVIDIA outputs, early display discovery and suspend restoration. Removing persistence's multi-user ordering would not remove the observed modules-load delay. Deferring the modules until a first game/CUDA command could race external-monitor login and resume; this round therefore changes neither kernel module timing nor persistence ordering. A separate measured trial must cover cold boot with GPU disabled/enabled, external output before login, game offload, `nix develop .#cuda` and suspend/resume before adopting that change. No boot-time speedup is claimed.
