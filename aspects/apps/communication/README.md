# Communication

Installs desktop communication clients: QQ, WeMeet, WeChat, Vesktop, and Thunderbird. The feature uses package availability and the selected session environment; it has no identity input. Thunderbird alone accepts optional `user.appearance` palette data.

It wraps QQ with PipeWire available for runtime loading, selects its Wayland or X11 backend from the active session, and requests Electron's XDG portal file dialog. The locked QQ package is closed source, version 3.2.34-2026-09-24, so its embedded Electron version and support for that switch cannot be established from the package recipe. This does not enable QQ screen sharing in Mango: the locked QQ picker is X11-only and Mango's rootless Xwayland has no target window. The optional Xorg session still requires a real call and capture acceptance test. Vesktop enables the system Vencord integration; its package pins Electron 43, and Obsidian uses nixpkgs' Electron 43 default (43.7.11); both use Electron's portal file-dialog default, which requires portal version 3. Thunderbird's package wrapper locks the Gecko portal file-picker preference; accounts and credentials remain interactive.

WeChat 4.1.13.26 uses an application-specific launcher with `QT_QPA_PLATFORM=xcb`, `QT_IM_MODULE=ibus`, and `IBUS_USE_PORTAL=1`. Its bundled Qt has an IBus path whose non-portal initialization requires an `ibus-daemon` executable; selecting the existing Fcitx5 IBus portal avoids that discovery requirement. This installs no second input-method daemon and changes no global input-method environment. Both the command and desktop entry use the wrapper, preserving arguments, `%U`, icons, and upstream desktop metadata. The selected Home Manager package is checked by `communication-wechat-ime`, including forced environment values, argument forwarding, and the complete desktop entry. Existing WeChat processes must exit normally before a new launch can use the wrapper, because WeChat is single-instance.

On 2026-10-25, a private environment demonstrated the portal `CreateInputContext` call, then the real Mango session showed `wechat frontend:ibus focus:1`; the user confirmed Chinese input and English switching in a chat field. This validates the three-variable launch recipe, not automatic activation of a later system generation. Xwayland scaling was not a visual acceptance target. Recheck this workaround after WeChat/Qt updates; evidence and upstream sources are in [the execution record](../../../docs/history/wechat-ime-2026-10-25.md).

Owned files are `default.nix`, `im.nix`, `checks.nix`, and `thunderbird.nix`; the feature owns the corresponding Home Manager package and Thunderbird declarations. These Nix files are private. Removing the feature removes package and application declarations on the next generation; it retains Thunderbird profiles, account credentials, chat histories, and application data.

Thunderbird's `seedThunderbirdUi` activation reads an existing default profile from `$XDG_CONFIG_HOME/thunderbird/profiles.ini` (falling back to `~/.thunderbird/profiles.ini`). It prefers the installation default, then the profile marked `Default=1`; it creates no profile or account. With an appearance selected, it merges the generated One Dark chrome into `chrome/userChrome.css` between `/* BEGIN nix-dotfiles managed Thunderbird theme */` and the matching END marker. The template uses Inter 13px with Noto Sans CJK SC fallback, compact toolbar/tab/header spacing, neutral surfaces and a 2px blue selection indicator. Native folder widths, layout, message list mode and toolbar customization remain user controlled.

The seed owns only this CSS block and the `// BEGIN nix-dotfiles managed Thunderbird UI` block in `user.js`. It seeds `toolkit.legacyUserProfileCustomizations.stylesheets=true` and compact `mail.uidensity=0` only when the preference is absent from `prefs.js` and personal `user.js` content. Explicit user settings take priority, including disabling custom stylesheets or choosing a different density. It never writes `prefs.js`, `userContent.css`, mail content colors, active theme preferences, remote content/security preferences, account definitions, filters or mail storage. CSS applies only to the main window, `about:3pane` and the `about:message` chrome wrapper; the message body is a separate document and retains its original presentation. No live palette writer or profile symlink is installed.

Personal bytes outside both markers and existing file permissions are preserved. Duplicate, incomplete or reversed markers and symlinked profile/config paths are refused before writing either managed file. An uninitialized profile is skipped until a later activation; existing clients must restart normally to load CSS. Removing communication stops this activation and removes its installed package declarations, while both marker blocks and all Thunderbird data remain. Remove just those blocks manually to stop the seeded appearance. Resources are private; `checks.nix` exports `communication-thunderbird-ui`, which tests the generated activation CSS and seed in isolated synthetic profiles.
