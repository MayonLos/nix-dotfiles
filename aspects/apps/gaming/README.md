# Gaming

Configures gaming tools for a selected user and routes shared NixOS support through `gaming-host`. The host side owns Steam, Gamescope and GameMode integration; the user side configures MangoHud and Prism Launcher. The user's GameMode group membership is part of this feature.

Outputs include Steam and host gaming support, MangoHud metrics, and Prism Launcher with the selected Java toolchains, FFmpeg, MangoHud, Gamescope, and GameMode support. When the user has an appearance palette, it installs Prism's One Dark theme from the public `desktop/session-support.qt-style.nix` factory plus a Prism-only stylesheet. Main-window top and instance action toolbuttons have transparent default surfaces, with a quiet border on hover and a blue border for pressed, checked, or focused states. Prism settings tabs use a clear blue underline, nested group boxes lose duplicate slabs while keeping checkable indicators visible, disabled editor fields remain readable, and dialog footer buttons use compact spacing. A native Prism cat pack supplies the low-contrast geometric prism in the instance library, and a native icon theme replaces only the top `cat` action while inheriting `pe_colored` for other icons. Select `One Dark` under Settings → Appearance → Theme, `One Dark Prism` under Icon Theme (stored ID `NixDotfilesPrism`), and `Nix Dotfiles Prism` under Cat Pack (stored ID `NixDotfilesPrism`) once. Prism owns these selection settings and account/instance state. GameMode does not change GPU clocks or PowerMizer on this laptop; PRIME offload remains a separate launch-time choice.

Owned files are `default.nix`, `host/`, `mangohud.nix`, `mcsrv.nix`, `prismlauncher.nix`, `resources/prism/`, and the explicit test hook `checks.nix`; implementation Nix files are private. Minecraft packaging is in `packages/mcsrv-mayon/`. Removing the feature withdraws package, service, group declarations, theme, icon theme and cat pack files when activated. It preserves Steam libraries, game saves, Prism instances, downloaded mods, launcher accounts, and Prism's selected appearance settings.

## Performance and launch commands

`game-run COMMAND [ARG ...]` probes `nvidia-smi -L` with a three-second timeout at launch, sets PRIME OpenGL/Vulkan offload variables only when a GPU is available, and executes `gamemoderun`. If NVIDIA is powered off/unavailable it clears inherited offload selectors, prints a fallback notice and launches on the default Intel GPU. `GAME_RUN_GPU=integrated game-run ...` skips the probe. It issues no GPU power-switching command and does not retry a game after it has started; the NVIDIA probe can wake a runtime-suspended GPU; a GPU disappearing after the probe still needs application handling. Arguments, signals and the game's exit code pass through `exec`.

Steam's FHS environment runs the same probe once when Steam starts and supplies both GameMode library ABIs. GameMode is not preloaded session-wide: inherited `libgamemodeauto.so.0` reached every Steam helper, and a blacklisted helper (the client's websocket `lsof` check) aborted inside libdbus, so Steam failed at startup with "Unexpected Transport Error (0x3008)". Enable GameMode per game with the launch option `gamemoderun %command%` (or `game-run %command%` to reprobe GPU availability at every game launch). There is no single supported launch-prefix setting covering both native Steam games and every Proton compatibility tool. Wrapping a custom compatibility tool covers only games that explicitly select it, can conflict with existing compatibility choices, and does not cover native games. This feature therefore preserves those choices and does not install a process watcher or edit Steam userdata. See [GameMode’s Steam instructions](https://github.com/FeralInteractive/gamemode#requesting-gamemode) and [Steam’s compatibility-tool contract](https://github.com/ValveSoftware/Proton#install-proton-locally). Restart Steam after changing GPU availability; its environment is a launch-time snapshot. Existing game launch options remain application-owned.

Prism is patched at its game-launch boundary to prepend `game-run` to the existing wrapper, including instance-specific wrappers. This preserves user settings and keeps the launcher UI outside GameMode. The replacement is exact and fails a package build if upstream changes that boundary. Existing Prism GameMode/discrete-GPU switches can stay as chosen; the wrapper rechecks NVIDIA and clears stale selectors before the game starts. Accounts, instances and launcher config are never rewritten.

On GameMode's first client, `gaming-mode-hook start` saves the current PPD profile (including a manually selected one), acquires `gaming-idle-inhibit.service`, then sets `performance`. On the last client, `end` restores that saved profile and releases only its own inhibitor. Duplicate hooks are idempotent; a runtime-directory file lock serializes concurrent calls with a ten-second acquisition limit. Each child command has a fifteen-second timeout and GameMode allows 150 seconds for recovery/start/rollback. Failure rolls back both actions; a failed restore retains a retry record and still releases the inhibitor. `gaming-mode-hook end` retries recovery, and `gamemoded.service` has the same recovery as `ExecStopPost` if the daemon exits. The inhibitor passes the manager-expanded `NOTIFY_SOCKET` as an argument: systemd 260’s safe fork in `systemd-inhibit` removes that environment variable in the child. The child restores only the notify address for `systemd-notify --ready`, after logind has granted the inhibitor. The inhibitor has no login wants and is `PartOf=gamemoded.service`; it holds logind **idle** only, not explicit suspend or manual lock. Locked Noctalia observes logind `BlockInhibited` in its screensaver service and suppresses automatic idle actions. Existing user caffeine state is untouched. The automatic screen-off/lock integration is verified from Mango/Noctalia source; Xorg xidlehook/xss-lock behavior remains a runtime validation item. A login session must have PPD permission; a denied profile change is logged and rolled back. GameMode 1.8.2 otherwise always calls privileged `cpugovctl`, even for `desiredgov=ignore`; the shared package adds that explicit opt-out so PPD is the sole governor owner. Split-lock changes, inaccessible RAPL sampling and GPU clock changes are disabled, avoiding repeated pkexec/PAM sessions. `ioprio=off` preserves the game’s inherited priority; the package fixes upstream’s accidental clamping of that sentinel. Rejected client requests now include the method and return code instead of an empty `gamemodeauto:` error. A second client fix checks for a disconnected cached D-Bus connection before waiting on a pending call. Steam runtime lsof reproduces the upstream NULL-pending-call assertion when preloaded; closing the cached socket now produces an error rather than aborting the process. This does not enable preloading into Steam helpers. Hooks do not coordinate independent users changing the system-global PPD profile. A power cut or SIGKILL of the entire user manager cannot run recovery; check the profile after such an event.

The locked scx_lavd (1.1.2) loop only changes its power mode from PPD when launched with `--autopower`; the selected no-argument autopilot has no public runtime mode setter. GameMode therefore leaves lavd's load-based policy running. It does not restart scx, write BPF state or enable the previously avoided `--autopower`.

NVIDIA cache variables are `__GL_SHADER_DISK_CACHE=1`, `__GL_SHADER_DISK_CACHE_SIZE=10737418240` (10 GiB), and `__GL_SHADER_DISK_CACHE_SKIP_CLEANUP=1`; Mesa gets `MESA_SHADER_CACHE_MAX_SIZE=10G`. NVIDIA's skip-cleanup requests retaining cache entries, so 10 GiB is not a guaranteed storage cap. Driver defaults choose the cache location under the user's cache directory; no cache is cleared on activation/removal. In Steam Settings → Downloads, check **Shader Pre-Caching** (wording/placement depends on client version) and optionally background Vulkan shader processing. The repository does not edit Steam's mutable settings. `proton-ge-bin` is exposed through `programs.steam.extraCompatPackages`; choose GE-Proton under the game's Compatibility settings when needed, rather than forcing every game to use it.

## Gamescope

`gamescope-run -- COMMAND` reads the current physical mode from `wlr-randr --json`; in Mango it chooses the output under the pointer via `mmsg get cursorpos`, otherwise the first enabled output. Xorg uses `xrandr --current`. `--output DP-1` reads that output's mode without moving the nested window; `--size 2560x1600 --refresh 165` bypasses discovery. Output mode discovery is read-only and the nested compositor does not reconfigure the host display.

Wayland sessions explicitly use `--backend wayland`. In the pinned 3.16.23, the SDL backend aborted after a harmless child exited on a private GPU-backed headless sway, while the native Wayland backend exited zero. This also avoids depending on SDL's window backend selection. Xorg keeps upstream backend selection; its renderer and shutdown still need an Xorg acceptance test.

The compositor is launched directly; its game child is launched as `gamescope ... -- game-run COMMAND`. The wrapper clears inherited PRIME selectors and removes only `libgamemodeauto` entries from the compositor's preload list, retaining Steam/MangoHud overlays. The child rechecks GPU availability and acquires GameMode normally. This restores the compositor's upstream GPU choice rather than forcing a particular vendor: with NVIDIA 595.71.05 rendering the compositor, the isolated 3.16.23 probe segfaulted on child shutdown even without GameMode; the Intel compositor exited cleanly. Explicit Vulkan driver overrides remain user-owned. If an outer Prism/user wrapper already registered the current PID, that registration lasts until Gamescope exits and the reaper removes it; removing preload before exec does not revoke existing requests. Real Mango, NVIDIA-rendered game content and HDR still need acceptance tests.

```sh
game-run ./game --arg
gamescope-run --render-size 1920x1200 --fsr --fps 90 -- ./game
gamescope-run --output DP-1 --fps 60 -- ./game
# Steam per-game launch option when this nested preset is wanted:
gamescope-run --render-size 1920x1200 --fsr --fps 90 -- %command%
```

The default frame cap is the current output's rounded refresh rate; the nested refresh and Gamescope frame limiter are both set to the requested cap. `--fsr` selects Gamescope FSR 1 spatial scaling; choose a lower `--render-size` to obtain upscaling. `--hdr` adds `--hdr-enabled`, `ENABLE_GAMESCOPE_WSI=1` and `DXVK_HDR=1` only as an explicit opt-in. Mango's locked source contains HDR/color-management support, but that does not prove the panel, EDID, nested Gamescope protocol and game all negotiate HDR correctly. Enable HDR on a compatible output separately and verify an HDR test image/game; no force-HDR workaround is applied. Nested Gamescope, NVIDIA fallback, refresh/VRR and HDR still require real display/game validation. This feature owns the three CLI packages, their scripts, GameMode hooks/unit and Steam launch environment in addition to the files above. It does not own Mango window rules or hardware power policy.

## Runtime regression checks

`gaming-launch` exercises launch arguments and hook rollback with command fixtures. `gaming-runtime` boots a separate NixOS VM, runs the real GameMode daemon, shell/preload chain, user manager, logind inhibitor and PPD CLI, and checks first/last-client and daemon-crash recovery, plus the preload destructor after a real process closes its inherited D-Bus socket. Its PPD D-Bus server is a fixture with three profiles; it does not establish real laptop firmware support, PPD authorization, or GPU performance. The same VM runs the selected Steam package’s FHS `steam-run` with `lsof -v` and asserts no global preload; it neither launches Steam nor runs Valve’s downloaded websocket helper.

`gaming-sdl3-wayland` runs LWJGL 3.4.0’s pinned Maven SDL native library on a private 2560×1600/1.5 headless compositor. It keeps the selected Prism package’s actual wrapper recipe and replaces only the launcher binary with an SDL probe; initialization, Wayland driver selection and window creation must succeed. A virtual pointer is registered on that private socket, without input events, because this bundled SDL crashes on a completely pointerless headless seat. `gaming-prism-launch` separately builds the actual patched launcher, guarding the exact C++ replacement. These checks do not launch a Minecraft instance or prove any modpack’s Java/native/rendering compatibility.

After applying: start Steam normally, then one game with `gamemoderun %command%`; inspect `gamemoded -s`, `powerprofilesctl get`, `systemctl --user status gaming-idle-inhibit` and `journalctl --user -u gamemoded -u gaming-idle-inhibit --since now-minus-test`. End the game and confirm GameMode inactive, the original profile restored, and no GameMode entry in `systemd-inhibit --list`. Repeat through Prism and verify the launcher itself does not keep GameMode active. Existing user overrides in `~/.config/gamemode.ini` or a game’s working directory can change upstream’s merged settings; this feature does not rewrite them.

## Minecraft server manager

The selected gaming user receives `mcsrv-mayon`, `restic`, and the Tailscale CLI. See [the command documentation](../../../packages/mcsrv-mayon/README.md) for CLI, data permissions, backups and integration limits. The Java map comes from `lib/java.nix`'s Temurin set and is passed as the non-secret `MCSRV_JAVA_MAP` session value. Servers and mutable settings live under `~/.local/share/mcsrv/<name>/`; deleting this aspect withdraws the manager but does not delete worlds, mods, configs, backups, or restic data. Prism instances are only read from an explicitly selected source and copied into a new server instance.

The only firewall exception is the root-owned `mcsrv-firewall@PORT.service` template for TCP 25565–25575. Polkit permits members of the feature-owned `mcsrv-firewall` group to start, stop, or restart only matching template instances. The unit runs an immutable Nix-store helper, never an instance script or user-writable command. On the default iptables backend the helper inserts/removes only its matching TCP port rule, marked `mcsrv-mayon-lease`, in NixOS's `nixos-fw` input chain. On nftables it adds a dedicated `mcsrv-ports` set with a 90-second element timeout and a uniquely marked rule in NixOS's `inet nixos-fw input-allow` chain; only its own set element is removed on stop. A fixed root-owned flock serializes concurrent port leases. The TUI must renew the service by restarting it. This opens the port to any reachable source address, including routed WAN or overlay networks: do not forward that router port unless intended, keep online authentication and whitelist enabled, and never expose RCON. Unsupported firewall backends do not receive the template and fail closed. By default the feature does not enable or start `tailscaled`; optional public NixOS settings `services.mcsrv-mayon.tailscale.{enable,operator}` explicitly select the existing NixOS daemon and operator integration. Tailscale integration uses the existing daemon only after the user opts in to configuring it. A running server process can still accept peers while a stale iptables lease remains, for at most 90 seconds; nft elements also expire after 90 seconds.

For headless server access, the recommended option is a private Tailscale tailnet; it avoids router port forwarding. Install/configure the NixOS Tailscale service separately when desired. The manager reports the existing Tailscale status/address; `t` in the TUI only shows setup guidance; `network NAME --connect` explicitly asks the existing daemon to join through `tailscale up` as an explicit CLI request. It does not read or store auth keys, and it does not enable, start, or stop `tailscaled`. playit.gg and self-hosted frp remain documented alternatives for users who need public access.

The manager's transient user units are started on demand and have no boot wants. They run as the selected user with a private per-instance working directory. `MCSRV_JAVA_MAP` points only to public Temurin store paths; no credential is added to the Nix store. Firewall rules and Java selections are runtime choices and require a rebuilt generation before changing the declared package set.
